# Reference

What each script, workflow and skill in this repository does, and the contract they are built to. New here? Start with the [quickstart](quickstart.md); for the daily routine read the [owner guide](owner-guide.md).

The contract first, then the parts built on it:

- `schema/factory.config.schema.json`: every setting a project makes in its `factory.config.yml`.
- `adapters/contract.d.ts`, `contract.js` and `contract-suite.js`: the interface a spec framework implements, and the shared tests every adapter must pass. OpenSpec comes first; others can follow.
- `adapters/openspec.js`: the OpenSpec adapter (changes under `openspec/changes/<id>/`). It runs the shared contract suite, and its `setup` is also tested against the real `openspec` CLI when that is installed.
- `adapters/paul.js`: the PAUL adapter (phases under `.paul/phases/`, plans in `.paul/ROADMAP.md`). A change is a phase directory's slug, a task a plan (`01-02` is `1.2`). The factory's settings live in a `factory.yml` beside the phase, `archive` writes an `ARCHIVED` marker there, and `tickTask` edits the roadmap line only. It passes the shared contract suite and is registered as `spec_source: paul`. A PAUL project gets two skills, not five (`lib/skills.js`): `skills/paul/run-spec/SKILL.md`, which builds one plan with PAUL's own APPLY then UNIFY (read from the project's local `.claude/commands/paul/`, which `doctor` checks), and the shared `babysit-pr`. `to-tickets`, `handover` and `resume-change` are OpenSpec-only: a PAUL project plans and resumes with PAUL's commands. Not yet run against a real PAUL project.
- `lib/github-source.js`: reads files of a branch that is not checked out, through the GitHub contents API. An adapter given it as its `source` reads that branch and is read-only.
- `examples/`: a sample config.
- `scripts/check-no-go.js`: fails when a factory branch or PR touches a protected path (the factory's baseline in `lib/baseline.js`, the project's `protected_paths`, and the change's own list).
- `scripts/pr-feedback.js`: one report of a PR's checks, unresolved threads and reviews, and when it has settled; also replies to and resolves threads. Which CI workflows it waits for is the config's `ci_workflows`.
- `scripts/babysit-round.js`: counts the fix rounds already pushed to a branch, so the cap (`max_babysit_rounds`) holds across separate runs.
- `scripts/factory-route.js`, `lib/router.js`, `lib/router-deps.js`: decide what one GitHub event means (run a task, babysit a PR, archive, escalate, or nothing). The rules are pure and take their label names, owner and id limit from the config; the GitHub and project reads go through the spec-source adapter and `lib/github-source.js`.
- `scripts/factory-issue.js`, `scripts/factory-ticket.js`, `scripts/factory-retry.js`, `lib/tracking-issue.js`: find or create a change's tracking issue; print the `Closes #n` line for a task's ticket; record a failed or successful run for the retry-once rule. Labels and owner come from the config, task and issue reads from the adapter.
- `scripts/factory-escalate.js`, `scripts/factory-sweep.js`, `scripts/factory-digest.js`: ask the owner to do an `(owner)` task; advance every open per-change PR the router would move (run hourly); post the daily digest. They take labels, owner and default branch from the config and read tasks through the adapter.
- `scripts/cleanup-merged.js`: tidies a local checkout after PRs merge (deletes branches whose remote is gone and whose tip is on GitHub, removes clean worktrees, returns to the default branch). Never deletes the config's `default_branch`.
- `lib/hooks.js`, `scripts/install-git-hooks.js`: write `.githooks/pre-commit` (refuse a commit on the default branch, then run `hooks.chain`) and `pre-push` (refuse a push to it), then point git at them unless the project already has hooks. Secret scanning is the project's own: list it under `hooks.chain`.
- `.github/workflows/no-go-guard.yml`, `factory-ci-relay.yml`, `factory-digest.yml`, `check-change-ids.yml`: reusable workflows (`workflow_call`) a project calls at a pinned ref. Scripts run from a checkout of the factory at that ref, never from the PR. `scripts/factory-env.js` hands them the config's Node version, Python version and install command. The runner's run job sets Python up (`actions/setup-python`) only when `runner.python_version` is set, before the install command: the hosted image's own Python is unpinned and refuses a plain `pip install`. `init` sets it for a Python project (from `.python-version`, else `requires-python`, else 3.12) and proposes `ruff check .`, `mypy .` and `pytest` as gates when the project names them.
- `.github/workflows/factory.yml`: the runner (route, sweep, run, escalate, report). The route job reads `factory.config.yml` once, from the default branch, and every other job takes its settings from the route job's outputs, so a PR branch cannot change the settings its own run uses. In the run job the project's rules and config are restored from the default branch, and the factory's code is moved outside the working tree, reached through `$FACTORY_DIR`. `lib/claude-args.js` builds the agent's caps and tool lists from `max_turns`, `spend_cap_usd`, `gates`, `runner.install` and `forbidden_commands`; `scripts/factory-check-change.js` fails a run early when its change is missing.
- `lib/reviews-settled.js`, `scripts/factory-reviews-settled.js`, `.github/workflows/reviews-settled.yml`: the `factory/reviews-settled` commit status on factory PRs. Pending until the quiet window is over, the checks are done and every `review_bots` bot has posted; success after, or after `reviews_timeout_minutes` since the last push (naming the bots that never posted). When the status turns to success it also dispatches the factory workflow for that PR, so the router marks it ready: the CI relay cannot, because GitHub starts no `workflow_run` for a run that waited for the owner's approval.
- `lib/run-record.js`, `scripts/factory-run-record.js`: after each agent run the run job uploads a small record (cost, duration, turns, denied tool calls) as the `factory-run-record` artifact; the daily digest lists the last day's runs with those figures and a total. A run with no record (it died early, or the agent's log was missing) says "cost unknown", never a guessed number. The record step also prints one line per tool call the agent was denied, because a run whose first commands are denied ends "successfully" having done nothing.
- `lib/denied-run.js`, `scripts/factory-denied.js`: the last step of the run job. A task or archive run that the agent was refused tool calls in and that made nothing (no PR for a first task, an unmoved PR head for a later one; the head is noted before the agent runs) is failed instead of ending `success`. It first comments the refused commands on the tracking issue, then the `report` job queues the one retry and a second failure asks the owner. A babysit pass is left out, and a run with no head noted or no denial count is never failed.
- `skills/`: the five agent skills (`run-spec`, `to-tickets`, `babysit-pr`, `handover`, `resume-change`) `init` copies into a project's `.claude/skills/`. Gates, owner, labels, branch prefix and review bots are read from `factory.config.yml`; scripts are reached through `$FACTORY_DIR`; the memory step is optional. They are written for `spec_source: openspec`.
- `templates/workflows/*`, `lib/callers.js`: the thin caller workflows `init` writes into a project (triggers, permissions, the pin). The relay's `workflow_run` list is rendered from `ci_workflows`. A pin must be a commit SHA or a `v*` tag.
- `lib/cli.js`: runs a script and turns a bad config or malformed spec file into exit code 2.
- `lib/adapters.js`: loads the adapter the config's `spec_source` names.
- `scripts/factory-init.js`, `lib/init.js`, `lib/detect.js`, `templates/agents-block.md`: `init`. Run from a project's root (`node $FACTORY_DIR/scripts/factory-init.js`), it detects the stack (Node, Python, Go, Rust), the owner and default branch from `origin`, and the project's CI workflow names, then writes `factory.config.yml` (never overwritten), the six caller workflows pinned to `--ref` (default: the commit of this checkout, which must be pushed), the five skills, a marked block in `AGENTS.md`, and `.githooks`; runs the spec source's setup; creates the missing labels; and prints the steps only the owner can do. It asks for `--gate` or `--ci-workflow` when it finds none, because a factory with no gate would call every change good. It decides everything before it writes, and a second run changes nothing. A differing workflow or skill is skipped unless `--force`; a project's own hooks are skipped unless `--adopt-hooks`. `--dry-run` writes and calls nothing. It adds `.agents/` (agent scaffold) to `.gitignore`, and warns about any file it writes that `.gitignore` already ignores, because `git add` would skip it without a word. `--apply-ruleset --ci-check <name>` (`lib/ruleset.js`) creates, or updates, one active branch ruleset named `software-factory` through `gh api`: both `factory/*` checks and the named ones required, force pushes and deletion blocked, no bypass. It leaves a branch that already meets this alone, and skips with a warning until the check callers are on the default branch. It merges the read-only command rules of `lib/allowlist.js` into `.claude/settings.json` (`permissions.allow`; other keys and rules stay; `--no-permissions` skips it); a test fails when a script is in neither the allowed nor the not-allowed list, and when a rule could write (`gh api`, merge, delete, force). `doctor` warns when a rule is missing.
- `scripts/factory-doctor.js`, `lib/doctor.js`, `lib/pin.js`: `doctor`. Run from a project's root with `gh` logged in; it checks the config, the adapter, the six callers and their pin (a branch fails; a `v*` tag that no ruleset protects warns; a ref GitHub lacks fails), the CI relay's trigger list against `ci_workflows`, the skills, git hooks, the five labels, the `CLAUDE_CODE_OAUTH_TOKEN` secret, and the default branch's ruleset (both `factory/*` checks required; your own gate and "Block force pushes" warn). Each gap prints the command that fixes it. A GitHub call that fails is a `skip`, so the file checks still run offline. Exit 1 on a failure, 0 otherwise. `--json` prints one object, `{ok, counts, results}`, with the same exit code, so an agent reads it without a paste. It cannot see whether the Claude GitHub App is installed, and it reads rulesets only, not classic branch protection.
- `docs/owner-setup.md`, `lib/owner-docs.js`: the steps only the owner can do (secret, Claude GitHub App, the branch ruleset and the order it must be done in, the approval policy, `FACTORY_DIR`). `init` prints each step with a link to its section and `doctor` prints the matching text and link for each gap; a test fails if a link's section is renamed.
- `scripts/factory-upgrade.js`, `lib/upgrade.js`: `upgrade`. Moves the `uses:` ref and `factory_ref` input of each caller to `--ref` (default: this checkout's commit), refreshes the five skills when this checkout is that commit, and prints the diff. Only the pin is rewritten, plus any permission a caller grants less of than this checkout's template (a reusable workflow cannot ask for more than its caller grants, so a run would fail at startup; `doctor` reports the same), plus the `workflow_dispatch` trigger on a `check-change-ids.yml` caller that predates it (the `reviews-settled` run dispatches it for a head GitHub never ran it on), so a project's own edits to a caller stay. A ref GitHub does not know is refused. `--dry-run` and `--no-skills` are available.
- `scripts/factory-new-change.js`: `new-change <id> [--title <text>]`. Creates an empty change through the spec-source adapter and prints the next step. It refuses, writing nothing, an id that is not lowercase letters, digits and hyphens, one over `change_id_max_length`, `archive`, an id an active change uses, and an id a now-archived change used (the router reads an archived id as finished, so it would never run). A title with a line break is refused because it becomes the proposal heading.
- `scripts/check-change-ids.js`: fails on a change folder whose id the factory cannot run.
